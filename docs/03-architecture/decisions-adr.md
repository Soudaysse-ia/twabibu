# Journal des décisions d'architecture (ADR)

Format : contexte → décision → conséquences. Une décision ne se change qu'en ajoutant un nouvel ADR qui remplace l'ancien.

## ADR-001 — TypeScript et monorepo pnpm/Turborepo (2026-11-11)
**Contexte** : site web d'abord, apps mobiles ensuite, plusieurs modèles Claude et développeurs amenés à contribuer. **Décision** : un seul dépôt, un seul langage, packages partagés (`contracts`, `tokens`, `ui`, `availability`). **Conséquences** : types partagés bout en bout ; une PR peut toucher web + api + mobile ; CI incrémentale.

## ADR-002 — Next.js pour le web, NestJS pour l'API, séparés
**Contexte** : SEO indispensable (pages soignants), apps mobiles à venir qui ont besoin d'une API stable et documentée. **Décision** : Next.js (SSR/ISR) consomme une API NestJS distincte avec OpenAPI. Pas de logique métier dans Next. **Conséquences** : deux services à déployer ; mais frontières claires, API réutilisée telle quelle par Expo et le back-office.

## ADR-003 — PostgreSQL + Prisma, Redis, pas de moteur de recherche dédié en V1
**Contexte** : volume comorien modeste (centaines de soignants, dizaines de milliers de RDV/mois). **Décision** : Postgres (full-text + trigram + contrainte d'exclusion anti-chevauchement), Redis pour verrous/caches/files. Meilisearch envisagé seulement si la recherche devient insuffisante. **Conséquences** : moins d'infrastructure, requêtes SQL à soigner.

## ADR-004 — Le téléphone comme identifiant patient, OTP SMS — *remplacé par ADR-016*
**Contexte** : aux Comores l'e-mail est peu utilisé ; le téléphone est universel. **Décision** : identifiant principal = numéro +269 vérifié par SMS ; e-mail facultatif ; mot de passe facultatif pour les patients. Pros : e-mail obligatoire. **Conséquences** : dépendance forte au SMS (coût, délivrabilité) → abstraction `SmsProvider`, surveillance, WhatsApp en V2 ; prévoir le changement de numéro.

## ADR-005 — Expo (React Native) pour Android et iOS
**Contexte** : équipe réduite, besoin de deux apps. **Décision** : Expo + Expo Router, partage de `contracts`, `api-client`, `tokens`, `i18n`, `availability` ; UI native réécrite (`ui-native`) avec les mêmes tokens. EAS Build pour les stores. **Conséquences** : pas de partage des composants web ; ergonomie 100 % native ; publication facilitée.

## ADR-006 — SMS via agrégateur international d'abord, opérateur local ensuite
**Contexte** : pas d'API publique documentée des opérateurs comoriens au 11/11/2026. **Décision** : démarrer avec Twilio ou Infobip (route Comores), négocier en parallèle une connexion directe (SMPP/HTTP) avec Comores Telecom et Yas (ex-Telma) pour baisser le coût et fiabiliser ; adaptateurs interchangeables. **Conséquences** : coût initial plus élevé par SMS ; expéditeur alphanumérique « Twabibu » à tester par opérateur.

## ADR-007 — Cartes OpenStreetMap/Leaflet et référentiel de localités maison
**Contexte** : Google Maps impose consentement et clé facturée ; la couverture des adresses comoriennes est partielle partout. **Décision** : Leaflet + tuiles MapTiler/OSM, table `Locality` (îles → villes/villages avec coordonnées) comme pivot de recherche, géocodage libre en complément, position du cabinet pointée manuellement par le soignant sur la carte. **Conséquences** : pas de coût Google ; qualité dépendante du référentiel à maintenir (back-office).

## ADR-008 — Pas de téléconsultation
**Contexte** : demande explicite du produit ; connectivité et cadre réglementaire incertains. **Décision** : aucun mode vidéo, aucun module WebRTC ; le modèle garde un champ `mode` (`IN_PERSON` seul) pour une extension future sans migration lourde. **Conséquences** : tunnel plus court d'une étape que Doctolib.

## ADR-009 — Hébergement VPS Docker Compose en UE
**Contexte** : coût, maîtrise des données, équipe réduite. **Décision** : voir `infrastructure-et-deploiement.md`. **Conséquences** : opérations à assumer (sauvegardes, mises à jour) ; scripts et runbooks obligatoires.

## ADR-010 — Code en anglais, interface et documentation en français
**Contexte** : modèles et bibliothèques en anglais, équipe et utilisateurs francophones. **Décision** : identifiants de code, commits et commentaires techniques en anglais ; UI, docs produit, specs et tickets en français. **Conséquences** : lexique bilingue dans `CLAUDE.md`.

## ADR-011 — Identité visuelle : logo officiel et bleu `#1956B4` (2026-11-11)
**Contexte** : le logo Twabibu (stéthoscope, wordmark, signature « À vos côtés, dans chaque temps de soin. ») a été fourni avec son fond bleu `#1956B4`. **Décision** : ce bleu remplace le bleu Doctolib comme `primary` ; la structure visuelle Doctolib est conservée (en-tête colorée, barre pilule, cartes blanches). Tokens v1.1.0. **Conséquences** : tous les composants prennent leurs couleurs des tokens ; aucun code ne référence `#107ACA`.

## ADR-012 — Écosystème patient · médecin · pharmacie dans le périmètre V1 (2026-11-11)
**Contexte** : la demande produit est de relier consultation, dossier médical, ordonnance et pharmacie (gardes, catalogue, commandes, livraison, espaces sponsorisés) pour que le médecin ne puisse plus travailler sans Twabibu. **Décision** : trois modules supplémentaires (SPEC-13 dossier médical, SPEC-14 ordonnance numérique, SPEC-15 pharmacies) entrent dans le périmètre ; Twabibu ne vend pas de médicaments et n'automatise aucun conseil médical (règles seulement) ; la validité juridique de l'ordonnance numérique est à confirmer (LEGAL-02), le PDF signé avec QR reste la référence. **Conséquences** : phases 2 et 3 allongées d'environ 4 semaines ; nouvelle app « Twabibu Pharma » (espace pharmacie dans `apps/web`, route `(pharma)`) ; référentiel médicaments à importer et maintenir ; rôle `PHARMACY_STAFF`.

**Mise à jour du 12/11/2026 (ADR-011)** : à la demande du porteur de projet, le bleu d'interface est éclairci (`primary` = `#2A6BCB`, le fichier logo garde `#1956B4`), les formes décoratives (cercles, blobs) sont supprimées et le produit est en thème clair uniquement, sans sections sombres en bas de page. Tokens v1.2.0.

## ADR-013 — Versions retenues au démarrage du code (2026-11-12)
**Contexte** : le plan citait Next.js 15, NestJS 11 et Prisma 6 ; au démarrage de la phase 0, les versions stables sont Next.js 16, NestJS 12, Prisma 7, TypeScript 7. **Décision** : Next.js 16, React 19.3, NestJS 12, Tailwind CSS 4.3, Zod 4, Vitest 5 ; **TypeScript 6.0** (typescript-eslint ne supporte pas encore la 7) ; **Prisma 6.19** (la 7 impose une nouvelle configuration du client, migration à faire dans un ticket dédié). Node 24 (`.nvmrc`). Tests de l'API avec `node --test` (métadonnées de décorateurs). **Conséquences** : les docs qui citent Next 15 / NestJS 11 se lisent « version majeure courante » ; une mise à jour majeure passe par un ticket et un ADR.

## ADR-014 — Sessions opaques au lieu de JWT + rafraîchissement (2026-11-12)
**Contexte** : le plan prévoyait un jeton d’accès JWT de 15 minutes et un jeton de rafraîchissement rotatif. Pour un site rendu côté serveur et des apps mobiles, cela impose un circuit de rafraîchissement dans chaque client, sans bénéfice à notre échelle. **Décision** : un jeton de session aléatoire de 32 octets (cookie `tw_session` httpOnly `SameSite=Lax` pour le web, en-tête `Authorization: Bearer` pour les apps), seul son SHA-256 est stocké dans `Session`, durée 30 jours, révocation immédiate à la déconnexion. Le site relaie l’API sur son propre domaine (`/api/*`). **Conséquences** : une lecture en base par requête authentifiée (à mettre en cache Redis si besoin) ; déconnexion et suspension effectives immédiatement ; la section 2 de `securite-et-donnees-sante.md` est à lire avec cet ADR.

## ADR-015 — Connexion des soignants par code SMS au démarrage (2026-11-12) — *remplacé par ADR-016*
**Contexte** : SPEC-07 prévoit e-mail + mot de passe fort + double authentification pour les comptes professionnels. Les cabinets pilotes utilisent surtout le téléphone, et le code SMS est déjà en place pour les patients. **Décision** : en phase 1, les soignants et secrétaires se connectent avec le numéro enregistré par leur cabinet et un code SMS ; une page de connexion distincte (`/pro/connexion`) refuse la création de compte. Le mot de passe et la double authentification (TOTP) restent à faire avant le lancement public (ticket SEC-05 à créer). **Conséquences** : la sécurité du compte pro repose sur la carte SIM ; sessions révocables immédiatement (ADR-014) ; à revoir avant d’ouvrir les comptes administrateurs.

## ADR-016 — L’e-mail comme identifiant, le SMS en secours (2026-11-13)
**Contexte** : un code de connexion par SMS coûte environ 0,03 à 0,20 $ vers +269, soit autant que 1 000 e-mails ; le porteur du projet demande de ne plus utiliser le téléphone pour créer un compte. **Décision** : patients et soignants s’identifient par leur adresse e-mail et un code à 6 chiffres envoyé par e-mail (5 min, 5 essais, renvoi après 60 s). Les confirmations, changements et annulations partent par e-mail ; le SMS ne sert plus qu’aux patients inscrits par le cabinet sans adresse e-mail. Fournisseur : **Brevo** au démarrage (300 e-mails gratuits par jour, société de l’UE), **Amazon SES** au-delà d’environ 50 000 e-mails par mois ; adaptateurs `FakeEmailProvider`, `BrevoEmailProvider`, `ResendEmailProvider` derrière `EmailProvider`. Comparatif chiffré : `docs/07-references/comparatif-email-sms.md`. **Conséquences** : la table `OtpCode` stocke un destinataire (`recipient`) au lieu d’un téléphone ; le téléphone devient facultatif sur le compte ; une partie des patients sans e-mail devra passer par le secrétariat (à mesurer pendant le pilote) ; mot de passe et double authentification des soignants restent à faire avant le lancement public (SEC-05) ; configurer SPF, DKIM et DMARC sur le domaine d’envoi avant la production.

## ADR-017 — Twabibu Pharma, espace séparé de Twabibu Pro (2026-11-13)
**Contexte** : les rôles `OWNER`/`ADMIN` existent dans les cabinets et dans les pharmacies ; une pharmacie ne doit jamais lire un agenda ni un dossier, un cabinet jamais une commande. **Décision** : routes `/v1/pharma/orgs/:orgId/*` protégées par `PharmaGuard` (membre d’une organisation de type `PHARMACY`) ; `ProGuard` refuse toute organisation de type `PHARMACY` ; interface distincte `/pharma/app` avec sa propre connexion. La dispensation est enregistrée quand une commande issue d’une ordonnance est marquée remise par un pharmacien. Twabibu n’encaisse rien : paiement au retrait ou à la livraison. **Conséquences** : un même compte peut appartenir à un cabinet et à une pharmacie sans mélange des droits ; les tests vérifient les 403 croisés ; le paiement mobile (MVola, Huri Money) reste en V2.

## ADR-018 — Back-office : application séparée, double authentification TOTP, rôles par compte (2026-11-13)
**Contexte** : SPEC-11 impose une app séparée, une 2FA obligatoire et des sous-rôles ; l’identité est déjà un code par e-mail (ADR-016), qui ne suffit pas pour des comptes capables de publier ou suspendre des soignants. **Décision** : `apps/admin` (Next.js, port 3200, jamais indexée) parle à `/v1/admin` ; `AdminGuard` exige `kind = PLATFORM_ADMIN`, un second facteur TOTP (RFC 6238, secret chiffré par `FieldCrypto`) validé sur la session depuis moins de 12 h, et un rôle qui ouvre la zone (`User.adminRoles` : `SUPERADMIN`, `VERIFIER`, `SUPPORT`, `FINANCE`). Chaque écriture passe par `AuditService` (table `AuditLog`, ajout seul). En local, le code `000000` est accepté pour le second facteur, comme pour le code e-mail ; la configuration interdit ce mode en production. Les comptes sont créés par `admin:create`, jamais par inscription. **Conséquences** : migration `20261114090000_admin_mfa` (`User.adminRoles`, `User.twoFactorEnabledAt`, `Session.mfaVerifiedAt`) ; la réinitialisation d’un second facteur perdu se fait par un super administrateur (écran à faire) ; aucun écran du back-office ne lit les tables médicales.

## ADR-019 — Les référentiels appartiennent au back-office (2026-11-16)
**Contexte** : `pnpm db:seed` réinjectait les référentiels à chaque exécution, y compris en production, en écrasant les valeurs ; une correction faite dans le back-office (nom de localité, date confirmée d’une fête islamique, médicament passé « contrôlé ») aurait été perdue au déploiement suivant. **Décision** : une fois créée, une ligne de référentiel (spécialité, localité, médicament) n’est plus modifiée que par le back-office ; le seed ne crée que les lignes manquantes. Les jours fériés d’une année ne sont semés qu’une fois, tant que l’année est vide (une date déplacée ou supprimée ne revient pas). Les adresses (slugs) ne changent jamais ; on désactive au lieu de supprimer ce qui est en usage. Le cache public de l’annuaire et des suggestions passe à 60 s. **Conséquences** : corriger une erreur du fichier de référence (`packages/contracts/src/reference`) sur une base existante se fait dans le back-office, pas en relançant le seed ; les listes statiques du site (libellés de repli de la recherche) ne connaissent pas les ajouts faits dans le back-office.
